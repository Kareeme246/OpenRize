2 · North star, and where iteration 1 sits

Rize's real engine (from its docs) tracks metadata only: the single active window's app name, window title, URL and timestamps, then segments that stream into time entries. Open source version of that is a three-layer build — the stopwatches in iteration 1 are not a throwaway toy, they are the manual entry path that has to coexist with automatic tracking later.

Iteration 1 · this plan

Shell + manual timers

  • Header, left sidebar, one page
  • Unlimited concurrent stopwatch widgets
  • Persisted across restarts, in Rust
  • macOS menu-bar icon showing active timers
Iteration 2 · not now

Background capture

  • Poll the active window on an interval
  • Write activity_sample rows
  • Idle detection + pause tracking
  • Exclude lists / privacy controls
Iteration 3 · later

Summary & rules

  • Segment samples into time entries
  • App & website rules, categorisation
  • Day/week focus and activity reports
◆

Tray icon moved into iteration 1 on your call. It is the natural home for a background tracker — the window becomes optional and the menu bar becomes the always-visible surface. That pulls three things forward with it: a tray.rs module that rebuilds its menu whenever timer state changes, close-the-window-hides-the-app semantics, and an explicit Quit item, because a resident app must offer a real way out. Everything else in iteration 2 stays deferred.

◆

Platform target: macOS is the shipping platform and Windows follows. Iteration 1 is therefore written with zero OS-specific capture code — nothing here queries a window, a process or an app name — so the Windows port in iteration 2 is a new tracker module behind the same trait, not a fork of the timer engine. Storage paths go through Tauri's app_data_dir(), which already resolves correctly on both. The one genuine macOS-only surface is the tray title (see section 6).

◆

Why manual timers first: they force the two hard primitives to exist early — a durable TimeEntry record and a monotonic-clock timer engine in Rust. Iteration 2 feeds that same engine instead of inventing a parallel one.

The brand accent cannot reach the menu bar. icon_as_template(true) hands the glyph to macOS to tint against the current bar, which is what makes it look native in light, dark and tinted menu bars — and it means #2aea83 is simply unavailable there. Active vs idle is therefore carried by glyph weight, as shown above: outlined when nothing runs, filled when something does. The textual summary lives in the tooltip instead.

◆

A native menu has no right-aligned action column. The earlier mock paired each timer's name with a Pause chip, which no real macOS menu can render — so each menu item now is the action, labelled Pause <name>. Same information, one row per timer, and no invented affordance.

6 · Data model, commands, and the menu-bar surface

The model is deliberately the classic accumulated + started-at pair. A tick counter or a per-second elapsed++ is the tempting simpler version and it drifts and breaks across sleep — this shape is both simpler and correct.

src/lib/timers.ts — shared shape
// elapsed = accumulatedMs + (running ? now - startedAt : 0)
export interface Timer {
  id: string;
  label: string;
  accumulatedMs: number;      // sum of completed runs
  startedAt: number | null;   // epoch ms when running, else null
  createdAt: number;
}

// The only pure function worth unit-testing.
export function elapsedMs(t: Timer, now: number): number {
  return t.accumulatedMs + (t.startedAt === null ? 0 : now - t.startedAt);
}

// 01:23:45, or 12:34 when under an hour — never a layout-jumping string.
export function formatDuration(ms: number): string;
src-tauri/src/commands.rs — IPC surface
// All take State<TimerStore>; all return the full list so the
// frontend never guesses at state it did not just write.
list_timers()                  -> Vec<Timer>
create_timer(label: String)    -> Vec<Timer>
start_timer(id: String)        -> Vec<Timer>
pause_timer(id: String)        -> Vec<Timer>
reset_timer(id: String)        -> Vec<Timer>
rename_timer(id: String,
             label: String)    -> Vec<Timer>
delete_timer(id: String)       -> Vec<Timer>

// Errors: Result<_, String> — a lock poison or a bad id
// must surface in the UI, not panic the app.

Why Rust owns the clock

  • Instant/monotonic time is immune to the user changing the system clock.
  • Rendering a strict-mode React tree must not be able to double-count or lose time.
  • Iteration 2's tracker writes to the same store from the Rust side — no cross-boundary races.
  • The frontend still ticks at 1 Hz purely to repaint; it never owns the number.

Why a JSON file before SQLite

  • Iteration 1 persists a handful of timers — SQLite is a dependency and SQL with no rows to justify it.
  • Written atomically (tmp + rename) so a crash mid-write cannot corrupt history.
  • Written synchronously on every mutation — a few KB at human click rate, and it makes "durable the moment you click" trivially true.
  • swap point Iteration 2 introduces SQLite for activity_sample; timers migrate with it.
◆

A running timer stores startedAt, so the elapsed time is correct even if the app was closed for an hour. Open decision: whether a timer that is still running when the app quits resumes on next launch (default in this plan) or auto-pauses at quit. Resuming is one less surprise; auto-pausing is the option that stops a forgotten tracker from claiming your whole night.

The menu-bar surface

src-tauri/src/tray.rs — grounded in the Tauri 2.11 tray API
// Cargo.toml: needs the feature
// tauri = { version = "2", features = ["tray-icon"] }

TrayIconBuilder::with_id("main")
    .icon(tray_icon(false))          // outlined stopwatch = idle
    .icon_as_template(true)        // macOS: system tint, no brand colour
    .menu(&build_menu(app, &active)?)   // ACTIVE timers only
    .show_menu_on_left_click(true)
    .on_menu_event(on_menu_event)    // any menu event; filter by id
    .build(app)?;

// On every state change: swap glyph + rebuild menu.
// set_icon_as_template sets icon AND template flag atomically,
// which is what stops the swap from flickering.
tray.set_icon_as_template(Some(tray_icon(!active.is_empty())))?;
tray.set_menu(Some(build_menu(app, &active)?))?;
tray.set_tooltip(Some(&summary))?;   // text lives here

Rules that keep it cheap and honest

  • Menu = active timers only — one item per running timer, each with its own Pause action. Paused timers appear in the window, never in the menu.
  • No live seconds, no count. The menu and glyph change only when timer state changes — never on a clock.
  • Item ids carry the timer id (pause:<id>) so on_menu_event dispatches straight to the store with no lookup table.
  • Two glyphs, not two colors: outlined when idle, filled when anything runs. set_icon_as_template swaps icon and template flag together so there is no flicker.
  • Tooltip carries the text ("2 running, 4 paused") since the bar itself stays wordless. Counts only: a timestamp in the tooltip would go stale between state changes. macOS and Windows support it; Linux does not.

Close is not quit

  • WindowEvent::CloseRequested → api.prevent_close() then window.hide(). A background tracker has to survive its window being closed.
  • Quitting happens only via Quit OpenRize in the menu (or ⌘Q), which flushes the store before exit.
  • Hiding the Dock icon (ActivationPolicy::Accessory) is later polish, not part of iteration 1.
◆

Cross-platform caveat, verified against the Tauri 2.11 docs: icon_as_template and set_icon_as_template are macOS-only — elsewhere Tauri falls back to setting the plain icon, so on Windows the glyph must look right as shipped rather than relying on system tinting. That is a reason to keep the tray art strictly monochrome with transparency. set_tooltip is unsupported on Linux only. By dropping the menu-bar title, iteration 1 avoids the one tray API that is genuinely macOS-exclusive and awkward elsewhere.

8 · Failure modes and risks

Named up front so none of them turns into a surprise during implementation.

RiskFailure it causesMitigation in this plan
App quits / crashes with timers running Lost or wildly inflated hours startedAt is persisted immediately on start; elapsed is derived, so nothing is lost. Quit behaviour is decision D4 below.
Machine sleeps or clock jumps Elapsed time is wrong on wake Monotonic clock in Rust, not Date.now(). Sleep behaviour is documented as known-rough for iteration 2 to refine.
Disk write interrupted Corrupt JSON = all timers gone Atomic tmp-file + rename; on unparseable load, rename the bad file aside and start clean rather than panic.
Many widgets running at once 1 Hz re-render storm, CPU burn in a background app Single 1 Hz tick in one hook, not one interval per card; the timer engine lives in Rust so the idle cost is one repaint per second.
Frontend invents state after a failed invoke UI shows a timer that does not exist on disk Every command returns the full list; the hook replaces state from the response and surfaces errors instead of assuming success.
Menu bar item becomes a second source of truth Window and menu disagree about what is running Both read the same TimerStore under one mutex; the menu is rebuilt from the store on every mutation, so it cannot drift.
Menu rebuilt on a clock Native menu churn every second, noticeable CPU on a 24/7 app Nothing in the tray is clock-driven: both the glyph and the menu update only on state change. Elapsed time is readable in the window, which is open on purpose.
Resident app with no visible window User cannot find or quit the app Menu always carries Open OpenRize and Quit OpenRize; ⌘Q still works; nothing is hidden behind the Dock only.
Tray glyph unreadable in the menu bar Icon looks broken in a dark bar, or the idle/active states are indistinguishable at 16px icon_as_template(true) so macOS tints it, monochrome art with transparency so Windows renders it as-is, and two glyph shapes rather than a colour change to carry idle vs active.
macOS/Windows tray differences Tray works on one dev machine only Icon, menu and menu events are portable. Only icon_as_template is macOS-only and it degrades to a plain icon set, so the art has to stand alone. No macOS-exclusive API is load-bearing.

9 · Decision log

Every decision this plan needed is now closed, so this section is a record rather than a questionnaire. The last column is what the implementation actually does — keeping it concrete makes drift obvious if we change our minds later.

IDDecisionChosenWhat it commits us to
D1 Who owns timer persistence Rust — JSON file in app_data_dir timers.rs writes atomically on every mutation. SQLite replaces it in iteration 2, when there are finally rows that justify a database.
D2 Who owns the clock Rust, monotonic time The frontend's 1 Hz tick only repaints. Elapsed is derived from startedAt, so it is correct at any moment, including after sleep or a clock change.
D3 Frontend styling Tailwind CSS v4 @tailwindcss/vite plugin plus a CSS-first @theme block in src/styles/app.css. No tailwind.config.js, no tokens.css.
D4 A timer still running at quit Resume on next launch Nothing special to implement beyond storing startedAt: time with the app closed simply counts, which is the honest behaviour for a background tracker.
T1 Menu-bar content Template icon only No set_title, no count. Idle vs active is a glyph shape swap. The brand accent is unavailable in the bar, and the text summary moves to the tooltip.
T2 The close button Hide, keep running prevent_close() then window.hide(). Quit happens only through the menu or ⌘Q, and both flush the store first.
T3 Control in the tray menu Pause active only The menu lists running timers with a Pause action each. Starting or resuming always happens in the window, which keeps the menu bounded no matter how many trackers exist.
